DOMUS — NOTES & FEATURE GUIDE
=============================

Project notes, feature documentation, and planning discussions for Domus.
(Filename: domus_notes.txt — formerly domus_features.txt)

Domus is a Telegram household assistant for a shared group chat (two users,
two apartments). Messages must start with the wake word "Domus" so the bot
knows when to respond. The bot uses OpenRouter for natural-language intent
parsing when an API key is set, and falls back to built-in rules otherwise.
Data is stored locally in SQLite (data/domus.db).


HOW TO TALK TO DOMUS
--------------------
Every command starts with "Domus" in the group chat, for example:
  Domus, add milk to the list

Social / meta:
  Domus, hello
  Domus, thank you
  Domus, help
  /start and /help also work as Telegram commands (no wake word needed).


================================================================================
IMPLEMENTED FEATURES
================================================================================


1. SHARED TO-DO & SHOPPING LIST
-------------------------------
Add, list, complete, and remove tasks. Items are shared for everyone in the
group chat. Tasks can have categories and due dates.

Categories: shopping, household, admin, maintenance, personal, general
(shopping is inferred automatically for grocery-style items).

Examples:
  Domus, add milk to the list
  Domus, add 2 milk to the list
  Domus, we need butter and eggs
  Domus, add pay rent by friday category admin
  Domus, please add going to the bank to the todo list. Have to do it tomorrow
  Domus, what's on the list?
  Domus, show me the shopping list
  Domus, export the list
  Domus, export the shopping list as csv
  Domus, clear the shopping list
  Domus, check off milk
  Domus, I bought the milk
  Domus, remove milk from the list
  Domus, we do not need butter anymore

Shopping quantities:
  - "add 2 milk" stores item name (milk) and quantity (2) separately in SQLite
  - Lists show "2× milk" when quantity > 1
  - Adding the same item again merges lines and bumps quantity (milk + milk → 2× milk;
    milk + 2 milk → 3× milk)

Todo-list adds infer category from the task (e.g. "going to the bank" → admin).
Shopping-list adds still default to category shopping.


1b. TASK CORRECTIONS (update_todo)
----------------------------------
Fix a recent task when you misspoke or the bot misunderstood — handled by
rules (not OpenRouter) so corrections are reliable.

Examples:
  Domus, I said the task is for tomorrow
  Domus, I meant going to the bank
  Domus, have to do it tomorrow

What happens:
  - Sets due date on the most recent open task (or a matching task by name)
  - "I meant …" also removes obvious mistaken entries (e.g. bad LLM adds)
  - Resets reminder_sent when the due date changes


2. ONE-TIME DUE-DATE REMINDERS
------------------------------
Tasks with a due date trigger an automatic Telegram reminder on or before
that date. Each task is reminded once (reminder_sent flag).

Examples:
  Domus, add call landlord by tomorrow category admin
  (Scheduler checks every 60 seconds and notifies subscribed chats.)


3. RECURRING REMINDERS
----------------------
Repeating household reminders run on a schedule without LLM cost. Supported
patterns: daily, weekly (by weekday), monthly (by day of month).

Examples:
  Domus, remind us every Tuesday to take out the trash
  Domus, remind me on the 1st of each month to pay rent
  Domus, remind us daily to water the plants
  Domus, list recurring reminders
  Domus, remove the take out the trash reminder

After a recurring reminder fires, the next due date is calculated automatically
(e.g. next Tuesday, next month on the 1st).


4. DAILY BRIEFING
-----------------
On-demand summary of the day, plus an automatic morning briefing at 08:00
(local time, configurable via BRIEFING_HOUR in .env).

The briefing includes:
  - Tasks due today
  - Overdue tasks
  - Shopping list preview
  - Other open tasks (up to 3)
  - A meal idea for the current time of day

Examples:
  Domus, what's on today?
  Domus, daily briefing
  Domus, what do I need to do today?


5. MEAL SUGGESTIONS
-------------------
Suggests meals from a built-in food database (18 seeded dishes). Avoids meals
eaten in the last 2 days. Shows prep time, notes, and which ingredients you
already have on the shopping list.

Examples:
  Domus, what should I eat for dinner?
  Domus, what can I eat for lunch?
  Domus, meal idea


6. COOK THIS → UPDATE SHOPPING LIST (plan_meal)
-----------------------------------------------
Pick a meal and Domus adds only the missing ingredients to the shopping list.

Examples:
  Domus, let's make curry with rice tonight
  Domus, I want to cook shakshuka
  Domus, make pasta aglio e olio

Reply example:
  Planning "Curry with rice": Added to the shopping list: coconut milk, curry
  paste. You already have: rice, vegetables.


7. WEEKLY MEAL PLAN
-------------------
Plans one dinner per remaining day from today through Sunday. Saves the plan,
shows it on request, and adds all missing ingredients for the week to the
shopping list (deduplicated).

Examples:
  Domus, plan meals for this week
  Domus, show the meal plan
  Domus, what's the meal plan this week?


8. WHAT'S MISSING FOR DINNER?
-----------------------------
Read-only check: compares a meal's ingredients against the open shopping list
without adding anything.

Examples:
  Domus, what's missing for pasta aglio e olio?
  Domus, what's missing for dinner?
  (If no meal is named, uses tonight's planned meal from the weekly plan.)


9. LOG MEALS
------------
Remembers what you ate so suggestions vary over time.

Examples:
  Domus, I had pasta for dinner
  Domus, we ate shakshuka


10. CONVERSATION LOGS
---------------------
Each bot session writes an append-only log to logs/session_YYYY-MM-DD_HH-MM-SS.log
(format: timestamp, user message — bot response). Logs are gitignored.


11. LIFECYCLE MESSAGES
----------------------
When the bot starts:  "Hi, I am awake and ready."
When the bot stops:   "Goodbye, I am going to sleep now."
(Sent to all subscribed group chats.)


12. INFRASTRUCTURE (behind the scenes)
--------------------------------------
  - Telegram polling (no public server required)
  - SQLite database with tables: todos, reminders, foods, meal_history,
    meal_plans, notification_chats (+ unused schema for meals, expenses)
  - APScheduler via python-telegram-bot job queue:
      * due-date reminders every 60s
      * recurring reminders every 60s
      * morning briefing daily at BRIEFING_HOUR (default 8)
  - Intent routing: rules first; OpenRouter only when rules return unknown
  - /private prefix or reply-to-bot → rules-only (no OpenRouter that turn)
  - Regex / rule-based fallback when OpenRouter is unavailable
  - Unit tests for intent parsing (tests/test_intents.py)
  - 45-second message timeout with user-friendly error
  - Long replies split at Telegram's 4096-character limit


12b. PRIVATE MODE & PRIVACY ROUTING
-----------------------------------
Skip OpenRouter for sensitive messages — local rules only.

  Domus, /private add doctor appointment friday
  (or reply to a Domus message with /private … — wake word optional on reply)

Duplicate shopping items merge instead of piling up — quantities bump on repeat
adds ("milk" twice → 2× milk; "2 milk" on existing milk → 3× milk).

PRIORITY BACKLOG — PRIVACY, NLP & MEMORY (discussion Aug 2026)
================================================================================
Shortlist for next implementation waves. Decisions below reflect Sebastian's
answers; open items marked TBD.


1. PRIVATE MODE (/private prefix or reply)
   DECIDED: Use a /private prefix or reply mode — not just the word "private"
   somewhere in the message. When active, that turn skips OpenRouter entirely
   (rules-only parsing). Both forms:
     Domus, /private add doctor appointment friday
     (reply to a Domus message with Domus, /private … or /private …)


2. RULES FIRST, THEN OPENROUTER
   DECIDED: Always run rule-based parsing first. If rules cannot resolve the
   message, pass it to OpenRouter. (Corrections already bypass the LLM today;
   this extends that pattern to all intents.)

   OPEN: If rules return a confident match, still call OpenRouter or skip it?
   DECIDED: Skip OpenRouter when rules succeed. OpenRouter only when rules
   return unknown or no actionable intent.


3. REDACTION LAYER BEFORE LLM
   DECIDED (long term): Configurable redaction patterns in .env (names,
   amounts, etc.) before text is sent to OpenRouter. Not required for v1 of
   the privacy pass — design with .env-driven patterns in mind.


4. OPENROUTER JSON HARDENING
   TBD — Sebastian currently unsure. Leaning toward a second LLM call to repair
   invalid JSON rather than only local string repair. Revisit after rules-first
   routing is in place and we can measure how often JSON still fails.


5. CLARIFY + CONVERSATION MEMORY ("brain")
   DECIDED: Prefer remembering context for the next message(s), not just
   one-shot clarifications. Broader vision: Domus should have a "brain" —
   structured memory in SQLite (not just raw chat logs). This is the main
   reason behind persisting data locally.

   LOOKUP LATER (Phase 2 memory design):
     - Per-chat / per-user short-term context (last intent, pending clarification)
     - Long-term user facts (preferences, apartment, dietary needs)
     - How much history to inject into OpenRouter vs. keep local-only
     - Relationship to conversation logs (logs/ — local only, never GitHub)


6. NATURAL-LANGUAGE TASK EDITS (no technical syntax)
   DECIDED: All edits must work in plain natural language. No required command
   structure like "edit … due …" — important for non-technical users.
   Examples should feel conversational:
     "Domus, actually that's due tomorrow"
     "Domus, rename that to pay rent"
     "Domus, I meant the bank thing, not the other task"


7. PER-USER PROFILES
   DECIDED: Domus should remember who wrote which message and store information
   about each person (Telegram identity + learned preferences), not just one
   shared household profile. Ties into diet filter, assignment, and stats.

   v1 candidate fields: telegram user id, display name, apartment, dietary
   prefs (vegetarian, allergies, dislikes).

   OPEN FOR SEBASTIAN: Which profile fields matter most day-to-day? What else
   should Domus remember about each person? (See HUMAN OPEN TOPICS below.)


8. DUPLICATE DETECTION / MERGE (shopping)
   DONE — quantity column in SQLite; repeat adds bump quantity (rules-only).


9. VOICE MESSAGE INPUT
   WANTED — DEFERRED. Include in roadmap; do not implement now. Whisper via
   OpenRouter or local model; privacy implications to decide when picked up.


10. AUTOMATED INTENT PARSING TESTS
    DECIDED: Yes. Golden-file tests from real log phrases (including session
    logs). Logs themselves stay local — see "Repository hygiene" below.


Repository hygiene
------------------
  - logs/ and data/ are gitignored — conversation logs and SQLite must NEVER
    be pushed to GitHub.
  - Test fixtures should use anonymised/synthetic phrases inspired by logs,
    not copy raw log files into the repo.

LANGUAGE — GERMAN SUPPORT (planning note)
================================================================================
Domus must eventually understand and respond in German. You use English in
the group chat for now while the bot is being built; German comes later. This
section records how to approach it without a big-bang rewrite.


Current state
-------------
  - Wake word stays "Domus" (same in both languages).
  - Rule-based parsing is English-only (regex, few-shot examples, help text).
  - OpenRouter prompts are English; the model can often parse simple German
    input anyway, but rules-first routing will miss most German phrasing
    until we add parallel patterns.
  - Replies from Domus are English (hardcoded strings in todos.py, meals.py,
    briefing.py, etc.).


Recommended approach (when we pick it up)
-----------------------------------------
  Phase A — Understand German input (keep English replies)
    - Duplicate critical regex/intent paths for German equivalents, e.g.:
        "füge Milch zur Liste hinzu" / "wir brauchen Butter"
        "was steht heute an?" / "was fehlt zum Abendessen?"
        "erinnere uns jeden Dienstag an die Mülltonne"
    - Extend OpenRouter SYSTEM_PROMPT with German few-shot examples.
    - Add German test fixtures alongside English in tests/test_intents.py.
    - Optional: detect language per message (simple keyword/heuristic) and
      route to a German rule set without mixing languages in one regex.

  Phase B — German replies
    - Extract user-facing strings into a small i18n layer (en/de JSON or
      Python dicts) — one place for "Added …", briefing headers, errors.
    - Choose default reply language: per-chat setting in SQLite, or mirror
      the language of the user's message, or household default "de".

  Phase C — German + voice together
    - Whisper (or similar) transcribes German audio → same intent pipeline.
    - Confirm transcription language; post-process German umlauts and
      compound words ("Einkaufsliste", "Müll rausbringen").
    - See HUMAN OPEN TOPICS → Voice & audio for open decisions.

What stays English for now (explicit)
-------------------------------------
  - Code, logs, commit messages, domus_notes.txt (dev docs).
  - Bot replies and /help examples until Phase B.
  - You may still write Domus in English in Telegram — rules cover that today.
  - Mixed DE/EN in one household is OK short-term; document preferred habit.

BRING! APP & DOMUS HOUSEHOLD APP (historical discussion — Aug 2026)
================================================================================

We previously used Bring! as our native shopping-list UI (fast check-off in the store, shared
household list). Domus handles NLP, meals, reminders, and tasks via Telegram.
The question was: should Domus mirror shopping into Bring! instead of growing its
own list UI — we now answer no: build our own app instead.


WHY TELEGRAM + BRING! TOGETHER
------------------------------
Telegram is a strong *input* layer (group chat, wake word, future voice).
It is a weak *shopping* layer (long text threads, no aisle-friendly check-off).

Bring! is the opposite: great in-store UX, weak as a household command center
(no "remind us every Tuesday", no meal-plan logic, no admin todos with due dates).

Sensible split if connected:
  Telegram → talk to Domus (brain)
  Domus    → todos, meals, reminders, briefing, SQLite history
  Bring!   → shopping display only (optional mirror target)


HOW THE UNOFFICIAL BRING! API WORKS
-----------------------------------
Bring! Labs does **not** publish an official developer API (no OAuth, no webhooks,
no partner docs). Integration uses the **same private HTTP endpoints** the mobile
app calls — reverse-engineered and wrapped by community libraries.

Primary library: **bring-api** (Python, PyPI, MIT)
  https://github.com/miaucl/bring-api
  https://pypi.org/project/bring-api/
  Also powers Home Assistant's official Bring! integration.

Auth flow:
  1. Create aiohttp ClientSession + Bring(session, email, password)
  2. await bring.login() — obtains session/token (same credentials as the app)
  3. Token refresh handled by the library on expiry

Core operations:
  load_lists()           → all lists on the account; each has listUuid + name
  get_list(listUuid)     → open items on one list
  save_item(uuid, name, spec?)  → legacy add (name + optional spec/note)
  complete_item(uuid, name)     → mark bought
  remove_item(uuid, name)       → delete from list

Modern batch API (what the current app uses):
  batch_update_list(listUuid, item, operation)
    operation = ADD | COMPLETE | REMOVE

  Each item is a dict:
    itemId  — display name (e.g. "Milk", "Milch")     [required]
    spec    — subtitle/note (e.g. "low fat", "2")     [optional]
    uuid    — stable item id on the list              [optional on add]

  Rules that matter for Domus:
  - ADD with same itemId updates spec on existing line unless uuid differs
  - Quantities map to spec ("2" or "2×") not a separate number field
  - COMPLETE/REMOVE need itemId + uuid (or itemId + spec as fallback)
  - Renaming itemId on an existing uuid is possible but breaks app refresh UX
  - No server push to Domus — clients poll (Home Assistant: ~90s)

Minimal async example (from bring-api docs):

  async with aiohttp.ClientSession() as session:
      bring = Bring(session, "EMAIL", "PASSWORD")
      await bring.login()
      lists = (await bring.load_lists())["lists"]
      list_uuid = lists[0]["listUuid"]
      await bring.save_item(list_uuid, "Milk", "2")
      items = await bring.get_list(list_uuid)
      await bring.complete_item(list_uuid, "Milk")

Caveats:
  - Unofficial — Bring can change endpoints; library maintainers adapt
  - Consumer ToS grey area for automation (fine for personal bot, risky as product)
  - Two sources of truth unless sync strategy is chosen deliberately
  - Domus quantity column ≠ Bring spec field (mapping is approximate)


ARCHITECTURE OPINION (assistant — Aug 2026)
-------------------------------------------
Do not rebuild Bring! inside Domus. Do not rush a native "Domus app" until
Telegram workflows are stable.

Credible growth path:
  Phase A — Telegram bot (now)
  Phase B — optional Bring! sync bridge for shopping (highest ROI next step)
  Phase C — read-only web/PWA dashboard for briefings (optional)
  Phase D — native app only if Telegram + Bring leave a real gap

Recommended first sync design: **Option A — write-only mirror**
  Domus shopping add/complete/remove → push to Bring
  Manual edits in Bring while shopping are OK; Domus SQLite stays primary
  Telegram reply never fails if Bring is down (log error, retry later)


SYNC OPTIONS (when/if we implement)
------------------------------------
  A. Write-only mirror — Domus master, Bring display (recommended first)
  B. Bring master — Domus reads Bring for shopping; SQLite cache only
  C. Two-way sync — uuid mapping + conflict resolution (overkill for 2 users)


FEATURE MAPPING (Domus → Bring!)
---------------------------------
  add 2 milk              → save_item / batch ADD, spec = "2"
  duplicate merge         → Bring loosely dedupes by itemId
  export list             → less needed if Bring is the UI
  clear shopping list     → batch REMOVE or list clear if exposed
  check off / bought      → complete_item / batch COMPLETE
  meal plan → ingredients → big win: auto-push missing items
  admin/personal todos    → Domus only, never Bring
  daily briefing preview  → poll Bring or use last sync cache
